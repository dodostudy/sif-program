## 1. 이번 프로젝트에서 실제로 반복된 작업 유형

md 문서와 커밋 이력을 교차 분석하면, 프로젝트 전 기간의 작업은 아래 6가지 유형의 반복이었다.

| # | 작업 유형 | 근거 문서 | 반복 횟수(체감) |
|---|-----------|-----------|:---:|
| A | **데이터 파이프라인** — Excel→JSON 변환, 파생컬럼 재계산, 매핑테이블, 정합성 검증 | Roadmap Phase 1, Roadmap3 전체 | 대규모 2회 + 수시 |
| B | **페이지/기능 구현** — 기존 아키텍처(FilterManager/ChartManager) 관례를 따르는 신규 페이지·기능 | Roadmap 2~7, Roadmap2 전체, Risk_Roadmap 전체 | 6페이지 × 다수 개정 |
| C | **검증/QA** — 로컬서버 + 헤드리스 크롬 스크린샷, 회귀 확인, 문법 체크 | Roadmap2/3, i18n_Roadmap 검증 절차 | 거의 모든 작업 후 |
| D | **다국어(i18n)** — 감사→번역→배선→검증 | i18n_Roadmap 전체 | Phase 0~4 + 잔여 수정 다수 |
| E | **문서/보고서 작성** — 공공기관 결과보고, 소개 문서, 로드맵 | result.md, result2.md, Want.md, int.md, prompt_result_report.md | 5건 이상 |
| F | **계획 수립** — 사용자 피드백 → 파일 단위 수정계획 + 우선순위표 | Roadmap2, Roadmap3, Risk_Roadmap | 3건 |

**문제였던 점 (에이전트 없이 진행한 비용):**

- 메인 대화 하나가 A~F를 전부 수행 → 파일 덤프·grep 결과·스크린샷 판독이 전부 메인 컨텍스트에 쌓여 **토큰 소모가 컸고**, 컨텍스트가 길어질수록 초반 규칙(예: "필터는 한글 canonical 값 유지")을 다시 설명해야 했다.
- 같은 삽질을 반복했다. 예: 헤드리스 크롬이 CDN 때문에 자연종료 안 되는 문제, `--dump-dom` hang, macOS에 `timeout` 없음, 프로파일 캐시가 옛 JSON을 무는 문제 — 이런 노하우가 **대화가 끝나면 휘발**됐다.
- 검증을 구현과 같은 컨텍스트에서 하다 보니 "내가 만든 것을 내가 확인"하는 구조라 누락이 생겼다 (EN 잔여 한글이 여러 차례 후속 커밋으로 발견된 것이 그 증거).

→ 이 세 가지가 정확히 **서브에이전트가 해결하는 문제**다: 컨텍스트 격리(토큰 절약), 지식의 md 파일 영속화(삽질 재발 방지), 역할 분리(객관적 검증).

## 2. 추천 에이전트 구성 (이 프로젝트 기준 5종)

### 2-1. `sif-i18n-keeper` ✅ 이미 생성됨 (`.claude/agents/sif-i18n-keeper.md`)

유형 D 담당. 룩업 계층 아키텍처, 번역 파이프라인, 검증 절차, 크롬 캡처 함정까지 이미 문서화되어 있다. **나머지 에이전트도 이 수준의 구체성을 목표로 작성하면 된다.**

### 2-2. `sif-data-pipeline` — 데이터 파이프라인 엔지니어

이번 프로젝트에서 **가장 아쉬웠던 에이전트.** Roadmap3(2,574→3,459건 확장)가 통째로 이 에이전트의 일이었다.

- **트리거**: 공단 아카이브 갱신, Excel 원본 교체, 파생컬럼 규칙 변경, db.json 정합성 의심
- **md에 담을 지식**:
  - db.json 스키마(15~18컬럼)와 파생 6종 규칙 — `기인물분류`/`12대기인물`(룩업), `KOEN공정`(작업명 룩업+판정), `위험도순위`/`3년간사고비중`(전건 재집계), `혹서기`(재해개요 월 정규식)
  - 원본 함정: 헤더 3행 병합셀, 데이터 4행 시작, 컬럼 순서 상이, `_x000D_` 잔재
  - 공종 재편 규칙: `12. 공통공사` → `12. 철거·해체` + `13. 기타`, 표기 정규화 2건
  - 매핑테이블은 코드 밖(`scripts/mapping/*.json`)으로 분리한다는 방침
  - **완료 기준**: 건수 대조 일치, 파생 전량 채움, 미매칭 0 또는 명시적 판정, 검증 리포트 출력
- **기대 효과**: 데이터 갱신은 연 단위 반복 예정(result2.md "연간 재해 데이터 업데이트 지속 추진"). 규칙이 md에 있으면 내년 갱신 때 처음부터 다시 설명할 필요가 없다.

### 2-3. `sif-page-builder` — 페이지/기능 빌더

유형 B 담당. 6개 페이지가 전부 같은 관례를 공유하므로, 관례를 md로 고정하면 신규 기능이 아키텍처를 깨는 일을 막는다.

- **트리거**: 신규 페이지 추가, 기존 페이지 기능 확장, 차트/필터/테이블 수정
- **md에 담을 지식**:
  - 모듈 관례: `FilterManager`(Observer, setDownstream cascading) / `ChartManager`(create 시 기존 인스턴스 destroy) / `DataLoader`(인메모리 캐시) / `utils.js`(aggregateBy, topN, buildTable, filterDB)
  - **철칙**: 필터·집계·등식비교는 한글 canonical 값, 화면 표시만 `tCat()` — i18n과 공유하는 최상위 규칙
  - UI 관례: 다크테마 기본(`bg-gray-950`, `chart-container`), datalabels `건수 (비율%)`, 드롭다운은 건수 내림차순 + `명칭 (N건)` 표기, line-clamp 금지(전문 표시), `@media print` 규칙, 모바일 1열 풀폭
  - 신규 문구·라벨 추가 시 **i18n-keeper에 인계**해야 한다는 체크 항목 (EN 잔여 한글의 주원인이 "기능 추가 후 i18n 미반영"이었음)
- **기대 효과**: Roadmap2의 19개 항목, Risk_Roadmap의 12개 작업 같은 대량 수정을 항목별 서브에이전트로 병렬 처리 가능.

### 2-4. `sif-qa-verifier` — 검증/QA 전담

유형 C 담당. **구현자와 검증자를 분리**하는 것이 핵심 가치.

- **트리거**: 기능 구현 완료 후, 커밋 전, 배포 후 확인
- **md에 담을 지식**:
  - 검증 순서: ① 문법(`node --check js/*.js`, JSON 파싱) ② 정적 감사(`i18n_audit.py`) ③ 로컬서버(`python3 -m http.server`) ④ 헤드리스 크롬 스크린샷 → Read로 직접 판독
  - 크롬 캡처 레시피(i18n-keeper와 공유): `--headless=new --virtual-time-budget=10000` + **백그라운드 실행 후 sleep→kill** (CDN 때문에 자연종료 안 함), `--dump-dom` 금지, 검증은 새 프로파일로
  - 페이지별 체크리스트: 6페이지 × (KO/EN × 데스크톱/모바일 × 인쇄) 매트릭스
  - 회귀 포인트: 카스케이딩 필터 연동, 차트 클릭 드릴다운, 엑셀 다운로드, localStorage(테마/언어) 유지
- **기대 효과**: 메인 대화는 "QA 통과/실패 + 실패 항목"만 받는다. 스크린샷 판독·서버 로그가 메인 컨텍스트를 오염시키지 않아 토큰 절약이 가장 큰 에이전트.

### 2-5. `sif-report-writer` — 공공기관 문서 작성자

유형 E 담당. `prompt_result_report.md`에 이미 프롬프트 자산이 있다 — **이것이 사실상 에이전트 md의 초안**이므로 승격만 하면 된다.

- **트리거**: 결과보고서, 소개 페이지 문안, 대외 공유 자료, 로드맵 문서화
- **md에 담을 지식**:
  - 공문 어체 변환표(~추진/~기여/~마련), 로마자 목차 + ○ 기호, A4 1~2장 분량 기준
  - 임팩트 패턴: 한 줄 인용문(`"2,574건을 5초 안에"`), before/after 코드블록, STEP 화살표 흐름
  - 프로젝트 고정 사실관계: 개발주체(행복+ 분당발전본부 안전관리실), 데이터 출처(KOSHA SIF, 직접 요청 확보), 저작권 제약(상업적 이용·변경 금지), 배포 URL
  - 문서는 `md.cf/`에 저장한다는 관례
- **기대 효과**: 보고서마다 어체·형식·사실관계를 재설명하지 않아도 됨. 숫자(2,574→3,459) 갱신 시 일괄 반영 체크리스트 역할.

### 만들 필요 없는 것 (솔직한 판단)

- **로드맵 설계(유형 F)**: 내장 Plan 에이전트/플랜 모드가 이미 이 역할. CLAUDE.md와 위 에이전트 md들이 충실하면 별도 에이전트 불요.
- **커밋/배포 에이전트**: 커밋 형식(`[영문] 한국어 제목` 등)은 CLAUDE.md 한 줄이면 충분. 에이전트로 만들면 오히려 오버헤드.
- **탐색 전용 에이전트**: 내장 Explore 에이전트가 있으므로 중복.

## 3. 에이전트 운영 방법론 — "지속 고도화"

에이전트 md는 한 번 쓰고 끝나는 문서가 아니라 **프로젝트의 경험이 축적되는 저장소**다. 이번 프로젝트에서 검증된 루프:

```
작업 요청
   ↓
메인 대화(지휘) ── 해당 에이전트 호출 (컨텍스트 격리)
   ↓
에이전트가 감사→실행→검증까지 완결 수행
   ↓
작업 중 발견한 함정·규칙 변화를 에이전트 md에 추기   ← ★ 고도화의 핵심
   ↓
다음 호출 때는 그 삽질을 반복하지 않음
```

**고도화 규칙 3가지:**

1. **삽질은 md로 승격한다.** 예: "헤드리스 크롬이 CDN 때문에 자연종료 안 됨 → sleep+kill" 같은 발견은 그 자리에서 에이전트 md의 ⚠️ 항목으로 추가. (sif-i18n-keeper에 실제 적용된 방식)
2. **완료 기준을 명시한다.** "미커버 0건", "미매칭 0 또는 명시적 판정"처럼 에이전트가 스스로 끝났는지 판단할 수 있는 기준이 있어야 재작업이 줄어든다.
3. **에이전트 간 인계 지점을 정의한다.** page-builder가 새 문구를 추가하면 → i18n-keeper 호출, data-pipeline이 db.json을 갱신하면 → i18n-keeper 재번역 + qa-verifier 회귀. 이 연쇄를 각 md에 한 줄씩 적어두면 누락(이번 프로젝트의 EN 잔여 한글)이 구조적으로 방지된다.

**토큰 절약 원리:**

- 서브에이전트는 파일 덤프·grep 결과·스크린샷을 **자기 컨텍스트에서 소화**하고 메인에는 결론만 반환한다. 이번 i18n Phase 3에서 5,347문단을 23개 배치 × 병렬 서브에이전트로 처리한 것이 성공 사례 — 같은 원리를 QA·데이터 검증에도 적용하면 된다.
- 메인 대화는 짧게 유지되어 초반 규칙이 컨텍스트에서 밀려나지 않는다.

## 4. 새 프로젝트 시작 체크리스트

이번 경험을 일반화하면, 다음 프로젝트는 이 순서로 시작하는 것을 권장:

1. **CLAUDE.md 먼저** — 언어 규칙, 기술스택, 구조, 데이터 흐름, 커밋 형식. (이번 프로젝트의 CLAUDE.md가 좋은 템플릿)
2. **역할 골격 4종을 빈 껍데기로 생성** — ① 빌더(구현 관례) ② 데이터(파이프라인+완료 기준) ③ QA(검증 레시피) ④ 문서(어체+형식). 프로젝트마다 이름만 바꾸면 되는 범용 구도다.
3. **첫 작업부터 에이전트를 통해 수행** — 처음엔 md가 얇아도, 3번 규칙(삽질 승격)을 지키면 프로젝트 중반쯤 md가 sif-i18n-keeper 수준으로 두꺼워진다.
4. **주기 작업은 에이전트 md에 절차로 고정** — 연간 데이터 갱신, 배포 QA처럼 반복이 확정된 작업이 1순위.

### 에이전트 md 범용 템플릿

```markdown
---
name: <프로젝트>-<역할>
description: <어떤 상황에서 호출하는지 — 트리거를 구체적으로. 메인 대화가 이 문장만 보고 위임 여부를 판단한다>
---

너는 <프로젝트>의 <역할> 전담 에이전트다.
목표: <한 문장. 지키면 안 되는 것(불변 조건)도 함께>

## 아키텍처 / 관례  ← 반드시 지킬 것
<파일 역할 표, 핵심 규칙 번호 목록>

## 작업 절차
<유형별 A/B/C 절차. 명령어는 복붙 가능한 형태로>

## 검증 (필수)
<완료 기준을 수치로. ⚠️ 알려진 함정 목록>

## 인계
<이 작업 후 호출해야 할 다른 에이전트>
```
